5. FEATURES STILL INCOMPLETE / NOT IMPLEMENTED (honest)
--------------------------------------------------------------------------------
[HIGH] Company & Branch selectors — NOT IMPLEMENTED (by design, not faked).
  - The data model is single-company-per-user: User.company_id is one FK; there
    is no user<->company membership table, and transactional queries are not
    branch-scoped. A real company/branch switch would require a schema change
    (membership) plus branch-dimension filtering across most endpoints.
  - The brief rightly rejects a label-only selector, so none was added. This is
    a genuine gap for any multi-company/multi-branch deployment and is called out
    here rather than hidden. Scope: medium-to-large backend change.

[HIGH] Incremental Alembic migrations — MISSING (production schema-evolution risk).
  - There is ONE migration (0001_initial) whose upgrade() calls create_all and
    downgrade() calls drop_all. The seed step also calls create_all.
  - Consequence: a FRESH deploy builds all current tables correctly, and an
    EXISTING database gains any NEW tables via the seed's create_all. But
    create_all does NOT alter existing tables, so a future COLUMN added to an
    existing table would NOT reach an already-migrated database. This session's
    additions were all new tables (covered), but the pattern is unsafe for
    ongoing schema change. Remediation: generate real autogenerated migrations.
  - Also: `alembic downgrade base` would drop_all — destructive by design; never
    run it against a database with data.

[VENDOR-BLOCKED] Live integrations — simulators/engines built, live wiring needs
  external access:
  - Color Service: simulator only; no real hardware tested.
  - E-invoice / E-way bill: full engines + a configurable GSP adapter exist, but
    no live call has been made — needs Webtel/Pinnacle GSP credentials + endpoint.
  - Bank feeds: CSV import works; no live bank API.

8. POSTGRESQL VERIFICATION RESULT
--------------------------------------------------------------------------------
A throwaway PostgreSQL 16 cluster was initialised and started locally, and the
concurrency test was run against it:
  tests/test_pg_concurrency.py — 1 passed.
It drives 12 threads drawing the same stock item at once and asserts the FIFO
engine never double-draws (consumed <= available, remainder never negative, stock
conserved) — exactly what the advisory lock + FOR UPDATE guarantee and SQLite
cannot test. The test is gated on PG_TEST_URL so the normal suite skips it.
Document-sequence / duplicate-posting-reference races: idempotency is enforced by
a unique posting_reference + find_existing; the posting path is atomic. A
dedicated multi-worker sequence-generation stress test under Postgres is NOT yet
written (recommended before production — see §15).
