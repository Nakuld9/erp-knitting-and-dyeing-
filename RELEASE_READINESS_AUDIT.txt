--------------------------------------------------------------------------------
[HIGH-1] Stock-vs-GL reconciliation breaks once any dyed fabric exists
--------------------------------------------------------------------------------
File     : backend/app/services/accounting/stock_reconciliation.py  (GROUPS)
Evidence : After ONE completed dyeing job, stock_ledger_reconciliation returns
           is_reconciled = False:
             greige/FABRIC sub-ledger = 29100.00
             GL 1070 (Greige)         = 0.00        difference = -29100.00
             GL 1085 (Finished)       = 29100.00    <- dyed fabric lives here
Cause    : GROUPS maps ALL ItemType.FABRIC to greige account 1070. Dyed fabric
           (and legacy FINISHED rolls) are valued into GL 1085, but there is no
           FABRIC-finished group and no partition of grey vs dyed layers.
Impact   : Acceptance criterion "Inventory valuation reconciles" and the
           Reports -> "Stock vs GL Reconciliation" screen are WRONG for any
           company that has run a dyeing job - the opposite of what the project
           advertises. test_stock_reconciliation.py only covers opening stock +
           yarn/chemical consumption, so it stays green.
Business : A core financial control reports a false discrepancy; finance cannot
impact     trust the headline inventory reconciliation.
Proposed : Partition FABRIC layers in the reconciliation groups - grey
fix        production-order items -> 1070, dyeing-output / finished-roll items ->
           1085 - and add a test that runs a full knit->dye flow then asserts
           reconciliation.

--------------------------------------------------------------------------------
[HIGH-2] BOM yarn issue moves the sub-ledger with NO GL entry until grey valuation
--------------------------------------------------------------------------------
File     : backend/app/services/bom/production.py  (issue_material, value_grey_output,
           cancel_order)
Evidence : Issue yarn via a BOM order, do NOT value grey yet, then reconcile:
             yarn sub-ledger = 456000.00
             GL 1060 (Yarn)  = 480000.00   difference = 24000.00
             is_reconciled   = False
Cause    : issue_material calls inventory.consume only; the yarn->WIP GL credit
           is deferred to value_grey_output. (The legacy record_production path
           posts yarn GL immediately; the new BOM path does not.)
Impact   : For any IN-PROCESS order (yarn issued, grey not yet valued) the GL
           overstates raw-material inventory and understates WIP - a genuine
           period-cutoff defect at month-end. If an order is ABANDONED or
           CANCELLED after issuing yarn, the discrepancy is PERMANENT:
           cancel_order releases reservations but neither reverses the yarn
           stock movement nor posts any GL. (Amounts are correct; only timing
           and cancellation handling are wrong.)
Business : Month-end trial balance / stock valuation misstated while production
impact     is in progress; permanent misstatement on cancelled orders.
Proposed : Post the yarn->WIP GL at issue time (and WIP->greige at valuation),
fix        or post a compensating GL/stock reversal in cancel_order for already-
           issued material; add tests for in-process and cancelled-after-issue
           reconciliation.

--------------------------------------------------------------------------------
[HIGH-3] Dyed fabric cannot be sold; finished-goods GL (1085) never clears
--------------------------------------------------------------------------------
Files    : backend/app/services/order_lifecycle.py (deliver_rolls, FABRIC_DELIVERY)
           backend/app/models/dyeing_cost.py (DyeingOutput.dyed_item_id)
Evidence : Dispatch/COGS operates only on FabricRoll ids. The dyeing job's dyed
           output is a synthetic FABRIC inventory item keyed by
           DyeingOutput.dyed_item_id (a bare UUID) with NO FabricRoll. Grep
           confirms dyed_item_id has no consumer outside the dyeing module and
           the reconciliation service.
Impact   : The required workflow "dyed fabric inventory -> sales -> accounting"
           is NOT achievable - there is no screen or service to dispatch/sell a
           dyed lot. The 1085 debit from dyeing is never relieved by COGS, and
           revenue/COGS matching for dyed goods is broken. This is a MISSING
           operational flow, not just a defect.
Business : You cannot actually sell the dyed fabric the factory produces through
impact     the system; finished-goods inventory accumulates with no sell-through.
Proposed : Materialise dyed output as FabricRoll(kind=FINISHED) (or extend the
fix        delivery path to accept dyeing-output items) so dyed lots flow through
           the existing dispatch/COGS path; add an end-to-end test
           (grey -> dye -> dispatch -> COGS).

--------------------------------------------------------------------------------
[MEDIUM-4] Accrual-side accounting requires a qualified Indian CA's review
--------------------------------------------------------------------------------
Files    : backend/app/services/accounting/posting_rules.py (GREY_PRODUCTION,
           DYEING_PRODUCTION); backend/app/services/dyeing/service.py; jobwork.py
Detail   : The grey/dyeing flow capitalises conversion, dyeing, chemical,
           finishing, testing, other, reprocess and OUTSIDE JOB-WORK costs into
           WIP, crediting Expenses Payable (2020) / Accounts Payable (2010),
           WITH NO purchase invoice and NO GST / input-credit treatment.
           The system now holds TWO conventions: the standalone job-work module
           EXPENSES processing (Dr 5110 Job Work Expenses / Cr 2010), while this
           flow CAPITALISES (Dr WIP / Cr 2020). Direct-cost P&L accounts
           (5020 Knitting Wages, 5090 Processing Charges, 5100 Finishing Charges,
           5110 Job Work Expenses) exist but are BYPASSED.
A CA must confirm:
   (a) which treatment (capitalise vs expense) is correct for the business;
   (b) whether accruing a liability for manually-entered costs without a vendor
       bill or GST is acceptable;
   (c) GST input-credit handling for job-work / testing services.
Business : Statutory correctness of inventory valuation and GST credits.
impact

--------------------------------------------------------------------------------
[MEDIUM-5] Loss / rejection / reprocessing lack explicit accounting control
--------------------------------------------------------------------------------
File     : backend/app/services/dyeing/service.py (complete_job, _accumulate)
Detail   : Normal process loss is absorbed into the good-output unit cost
           (acceptable). But REJECTED quantity is only excluded from saleable
           output, so its share of cost is silently absorbed into good output -
           there is NO abnormal-loss write-off to a P&L loss account and no
           rejected-goods inventory. REPROCESSING records a reprocess_cost/qty
           but does not re-feed material as a distinct inventory flow.
Impact   : For a factory with real rejection, the cost of good output is
           overstated and abnormal losses are hidden in inventory value.
Proposed : Define a rejection/abnormal-loss policy and post write-offs to a loss
fix        account; model reprocessing as an explicit re-entry if required.

--------------------------------------------------------------------------------
[MEDIUM-6] GL posting depends on accounting being provisioned and the period open
--------------------------------------------------------------------------------
Files    : backend/app/services/bom/production.py (value_grey_output)
           backend/app/services/dyeing/service.py (issue_grey, complete_job)
           backend/app/services/company_provisioning.py
Detail   : Grey/dyed valuation now REQUIRES a configured voucher type, posting
           rules (default fallback - OK) and an OPEN accounting period for the
           voucher date, else it raises ClosedPeriodError / PostingError.
Impact   : A newly provisioned company database without periods covering the
           valuation date will FAIL production valuation operationally.
Proposed : Ensure provisioning seeds periods for the relevant range; surface a
fix        clear operator error; consider a provisioning health check.
